실험 개요

V4에서 실제 API를 붙인 앱에 단위 테스트를 추가하는 작업입니다. 프로덕션 코드를 수정하지 말고, 5가지 시나리오(초기 로딩·도시 선택·즐겨찾기·에러·성공)를 JVM 유닛 테스트로 커버하라는 동일한 요구사항을 세 AI에게 주었습니다.

비교 초점
각 AI가 ViewModel의 Repository 의존성을 테스트 환경에서 어떻게 격리하는지를 봅니다. 아키텍처가 다른 세 프로젝트에서 모킹 전략이 어떻게 달라지는지가 핵심입니다.
핵심 발견
Claude는 MockK로 싱글톤 Repository를 모킹했고, Codex는 MockK 없이 JVM URL 인터셉터를 직접 구현했으며, Gemini는 MockK + Turbine(Flow 전용 라이브러리)를 추가로 선택했습니다.
공통 결과
세 AI 모두 5개 테스트를 최종 통과시켰습니다. Codex만 1차 실행에서 3개 실패 후 자가 수정해 통과했고, Claude와 Gemini는 첫 시도에 전부 통과했습니다.

prompt_v5.txt · 단위 테스트 작성

You are adding unit tests to the existing WeatherNow Android app in this directory.

This is V5 of an AI comparison experiment. The app was built through V1–V4 and now fetches real weather data from Open-Meteo API.
Read the existing code first, then add tests without modifying production code.

Goal:
Write unit tests for the ViewModel (and Repository/data layer if it exists separately).

Requirements:
1. Write tests that cover these scenarios:
   - Initial loading state (isLoading = true on start)
   - City selection changes the selected city
   - Favorite toggle works correctly (set and unset)
   - Error state is set when the network call fails
   - Successful data fetch clears loading and error states
2. Use kotlinx-coroutines-test for coroutine/Flow testing (TestScope, runTest, Turbine optional).
3. Use MockK or a hand-written fake — your choice. Do NOT use Mockito.
4. Add only the test dependencies you need to app/build.gradle.kts (testImplementation scope).
5. Tests must be in src/test/ (JVM unit tests, not instrumented).
6. Ensure ./gradlew test passes with all tests green.

After implementation:
- Run ./gradlew test.
- Report how many tests passed, how many failed.
- Briefly describe what each test covers.
- Confirm the test run result.
모킹 방법(MockK vs 직접 구현)과 Turbine 사용 여부는 AI의 자율 선택 사항으로 남겼습니다. 각 프로젝트의 아키텍처가 다르므로 같은 요구사항에서도 접근 방식이 달라질 것이라고 예상했습니다.

07

관찰 및 인사이트

관찰 항목내용
V4 아키텍처 → V5 테스트 복잡도 Claude의 V4 WeatherRepository 분리 설계가 V5에서 간결한 테스트(140줄)를 가능하게 했습니다. Codex의 V4 통합 설계는 MockK 진입점이 없어 URLStreamHandlerFactory라는 우회책이 필요했고 결과적으로 245줄의 가장 긴 테스트 코드가 됐습니다. 설계 결정의 영향이 다음 단계로 전파된 사례입니다.
Codex의 독창적 접근 MockK 없이 URL.setURLStreamHandlerFactory()로 JVM의 https:// 핸들러 자체를 교체했습니다. 외부 라이브러리 의존 없이 프로덕션 코드를 건드리지 않고 HTTP 계층을 완전히 격리한 방법입니다. 단, 자가수정이 필요했던 유일한 AI이기도 합니다.
Gemini의 추가 선택 — Turbine 프롬프트에서 "Turbine optional"로 제시했을 때 Gemini만 Turbine을 채택했습니다. Flow 방출 시퀀스를 검증할 수 있어 테스트 표현력이 높아지지만, 의존성이 추가됩니다. 나머지 두 AI는 선택하지 않았습니다.
Dispatcher 선택의 차이 Claude·Gemini는 StandardTestDispatcher(코루틴 실행을 수동 제어)를 선택한 반면, Codex는 자가수정 과정에서 UnconfinedTestDispatcher(즉시 실행)로 전환했습니다. Codex의 ViewModel이 mutableStateOf (Compose State)를 사용해 Flow 기반의 두 AI와 상태 관찰 방식이 달랐기 때문입니다.
실행 시간과 자가수정 Gemini(231초)가 가장 빠르게 완료했고 Codex(256초)가 뒤를 이었습니다. Codex는 자가수정 과정에서 시간이 추가됐음에도 Claude(428초)보다 빠릅니다. Claude는 캐시 활용도가 높았지만 더 많은 검증 단계를 거쳤습니다.
