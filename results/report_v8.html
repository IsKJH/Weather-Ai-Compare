실험 설계
V7에서 Room DB로 저장한 즐겨찾기 도시를 WorkManager가 읽어서 15분마다 안드로이드 알림을 발송합니다. Android 8.0+ 알림 채널, Android 13+ 런타임 권한, 앱 시작 시 스케줄 등록이 필수 조건입니다.
핵심 관찰 포인트
이번에는 V7과 달리 세 AI 모두 기존 테스트를 수정하지 않았습니다. 대신 Worker 내부의 코루틴 패턴과 권한 체크 위치에서 설계 철학 차이가 드러났습니다.
V7 연속성
Room에 저장된 즐겨찾기 도시 인덱스를 Worker가 읽어서 알림 내용을 결정합니다. V7의 DAO 접근 방식(Claude nullable, Codex Repository, Gemini direct)이 Worker 구현에도 그대로 이어집니다.

⚠️
Gemini — runBlocking 안티패턴: CoroutineWorker.doWork()는 suspend fun으로 선언되어 코루틴 컨텍스트에서 실행됩니다. Gemini는 이를 non-suspend override fun doWork()로 선언하고 내부에서 runBlocking으로 감쌌습니다. 빌드는 통과하지만 Worker 스레드를 블로킹하는 구조로, 배터리 효율과 Doze 모드 동작에서 예기치 않은 결과를 낳을 수 있습니다.
🔒
Codex — 이중 권한 방어: Android 13+ 권한을 MainActivity에서 요청할 뿐 아니라, Worker 내부에서도 canPostNotifications()를 통해 발송 직전 다시 확인합니다. 권한이 사후에 취소되더라도 알림 발송 예외를 방지하는 가장 방어적인 접근입니다.
🗂️
Codex — 관심사 분리 일관성: V7에서 FavoriteCityRepository 인터페이스로 분리했던 것처럼 V8에서도 WeatherNotificationScheduler를 별도 클래스로 분리했습니다. Worker 등록 로직이 Application 클래스에 섞이지 않아 테스트와 교체가 쉽습니다. 반면 Claude·Gemini는 Application 클래스에 직접 인라인했습니다.
❓
Codex — 왜 V8에서 목 데이터를 썼나: Codex는 V4부터 Open-Meteo 실 API를 사용해왔습니다. 그런데 V8 Worker에서는 mockConditionForCity(cityIndex)로 하드코딩된 날씨 상태("맑음", "구름많음" 등)를 반환했습니다. 이유는 Worker의 책임 범위를 "알림 발송"으로 한정하고 네트워크 지연 실패를 Worker 재시도 루프와 분리하려는 설계 판단으로 보입니다. 알림 신뢰성(네트워크 없어도 항상 발송)을 API 정확성보다 우선했습니다. Claude·Gemini는 반대로 실 API를 Worker 안에서 직접 호출하여 실시간 날씨를 제공하되, 실패 시 Result.retry()로 대응했습니다.

Gemini — 테스트 중 자가 발견한 버그 4개: 빌드는 통과했지만 실기기 설치 시 ClassNotFoundException 발생. 원인: ① kotlin-android 플러그인 누락 ② doWork() non-suspend 선언 ③ AGP 9.2.1 등 실험적 버전 사용 ④ gradle.properties에 android.useAndroidX=true 누락. Gemini가 직접 모두 수정한 뒤 알림 발송 성공.

06

최종 평가

Claude
실 API 연동으로 가장 완성도 높은 알림 내용, 정석 suspend 패턴, 깔끔한 최소 구현. 별도 클래스 없이 Application에 직접 통합.
Codex
가장 빠르고 토큰 효율 최고. Worker 내 이중 권한 체크, BigTextStyle 알림, 커스텀 아이콘, Scheduler 클래스 분리까지 — 세부 완성도가 가장 높음.
Gemini
실 API 연동, 빌드 성공. 그러나 runBlocking 안티패턴이 명확한 기술 부채. 도구 오류로 시간도 가장 길었음.
🏆
V8 MVP — Codex: 속도(410초)·토큰 효율(74,945)·구현 완성도 세 항목 모두에서 앞섰습니다. 특히 권한 이중 방어와 알림 UX(BigTextStyle + 커스텀 아이콘)는 Claude·Gemini에 없는 추가 배려입니다. 목 데이터 선택은 신뢰성과 단순성을 우선한 실용적 판단으로 볼 수 있습니다.
📐
V7 → V8 일관성: Codex는 V7의 Repository 인터페이스 패턴을 V8의 Scheduler 분리까지 이어갔습니다. Claude는 V7의 nullable 파라미터 실용주의를 V8에서도 유지했고, Gemini는 V7에서 테스트를 직접 수정한 것처럼 V8에서 코루틴 패턴을 어겼습니다. 두 버전에 걸쳐 각 AI의 설계 철학이 일관되게 나타났습니다.
