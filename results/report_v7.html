03

테스트 호환 설계 전략

Room DAO를 ViewModel에 주입하면 기존 단위 테스트가 DAO 없이 ViewModel을 생성할 수 없게 됩니다. 세 AI가 이 문제를 각각 다른 방식으로 해결했습니다.

AI 전략 핵심 코드 장점 단점
Claude DAO nullable 파라미터
DAO가 null이면 DB 작업 생략		 class WeatherViewModel(private val dao: FavoriteCityDao? = null) 기존 테스트 코드 무수정. 최소한의 변경. null 체크가 프로덕션 코드에 남음. 타입 안전성 약함.
Codex Repository 인터페이스 + NoOp
테스트에선 NoOp, 프로덕션에선 Room 구현체		 interface FavoriteCityRepository
object NoOpFavoriteCityRepository		 의존성 역전 원칙(DIP) 적용. 테스트·프로덕션 교체 용이. 가장 확장성 높음. 파일 5개 추가로 코드량 증가.
Gemini 기존 테스트 직접 수정
DAO를 MockK로 mock해서 테스트에 주입		 val mockDao = mockk<FavoriteCityDao>() 프로덕션 코드가 가장 단순하고 명확. V5 원칙("기존 테스트 무수정") 위반. 테스트 변경 시 DAO 구현 변경도 필요.
🏆
Codex의 Repository 인터페이스 접근이 가장 설계 지향적입니다. 의존성 역전 원칙을 적용해 테스트에서 NoOp 구현체, 프로덕션에서 Room 구현체를 주입하는 구조입니다. Hilt 같은 DI 프레임워크 도입 시에도 인터페이스만 바꾸면 됩니다.
💡
Claude의 nullable DAO는 실용적 선택입니다. 기존 테스트를 한 줄도 건드리지 않으면서 가장 적은 코드 변경으로 목표를 달성했습니다. 다만 dao?.upsert() 형태의 null 체크가 프로덕션 코드에 남는 것은 타입 안전성 측면에서 아쉽습니다.
⚠️
Gemini는 기존 테스트를 수정했습니다. 프롬프트에 "기존 테스트를 수정하지 말 것"을 명시했는데, Gemini는 DAO mock을 추가하는 방식으로 테스트를 변경했습니다. 프로덕션 코드는 가장 단순하지만, 지시 이행 정확도에서 차이가 있습니다.
